XIP

Dedicated SPI master for execute-in-place, separate from any general-purpose peripheral SPI. Two mutually exclusive engines share one physical bus, switched by CONFIG's ENABLE bit: a fetch engine that lets the CPU execute code directly out of an external SPI NOR flash, and a generic byte-at-a-time write engine for whatever setup that flash needs first.

Engines

CONFIG bit 2, never both active at once
ENABLE = 1 Fetch engine Once enabled, jumping into the flash window (see memory.html) starts fetching instructions from the external flash automatically. There is no further register interaction: the hardware issues one 0x03 (READ) command per cache miss on its own. The write engine is disabled while this one is active.
ENABLE = 0 Write engine A generic byte-at-a-time SPI master for whatever setup the flash needs before XIP can be turned on (Write Enable, Page Program, etc). This controller doesn't know or care about SPI NOR opcodes, it just shifts bytes: CS_ASSERT holds chip-select across a multi-byte command, and each TX_DATA write starts one 8-bit, full-duplex transfer.
Switching engines mid-fetch

Clearing ENABLE while the CPU is executing out of the flash window cuts off the instruction stream it's currently running from. Software only ever switches engines while running from Boot ROM or RAM, never from flash itself, the same rule tinymcu_xip.h documents on tinymcu_xip_fetch_enable()/tinymcu_xip_fetch_disable().

A minimal boot sequence

Software configures the clock mode, then either enables the fetch engine and jumps into the flash window, or talks to the flash directly first:

tinymcu_xip_configure(0, 0, 0, 0);
tinymcu_xip_fetch_enable();
/* jump into XIP_FLASH_BASE..XIP_FLASH_END now */

or, to program the flash first from the write engine (CONFIG.ENABLE starts at 0 after reset, so no explicit disable is needed on a cold boot):

tinymcu_xip_configure(0, 0, 0, 0);
tinymcu_xip_cs_assert();
tinymcu_xip_transfer_byte(0x02); /* Page Program */
tinymcu_xip_transfer_byte(addr_hi);
tinymcu_xip_transfer_byte(addr_mid);
tinymcu_xip_transfer_byte(addr_lo);
tinymcu_xip_transfer_byte(data);
tinymcu_xip_cs_release();
tinymcu_xip_fetch_enable();

Notes

One entry, one cache

The fetch engine holds only its most recently completed transfer (last_data/last_addr in tinymcu_imem_xip.vhd). A cache hit on the same address skips the SPI transaction entirely; any other address triggers a fresh one.

A fetch here stalls the pipeline

Unlike Boot ROM/RAM's fixed one-cycle read, an XIP fetch takes a full SPI transaction to complete, and fetch_stall_o holds the whole pipeline for it. See pipeline.html's fetch_stall card for why that stall is kept separate from an ordinary EX-stage bus wait.

24-bit address only

The fetch engine's opcode/address header is fixed at 8 bits of opcode plus 24 bits of address (see XIP_TOTAL_BITS), so the addressable flash window tops out at 16 MB (XIP_FLASH_BASE..XIP_FLASH_END in tinymcu_pkg.vhd, see memory.html).
