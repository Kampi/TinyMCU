UART

One transmit and one receive shift register, framing configured via CONFIG (data bits, stop bits, parity), optional RTS/CTS flow control, and a single RX_READY interrupt whose flag stays tied to STATUS until the received byte is actually read.

Framing

CONFIG bits 5:0, decoded by databits_reg / stopbits_reg / parity_reg

Three small lookup functions turn CONFIG's 2-bit sub-fields into the actual values the Tx/Rx state machines use. Both Tx_Idle and Rx_Idle call all three at the start of every frame, latching the result into local variables for that one transmission/reception - a CONFIG write mid-frame never disturbs a frame already in flight.

FieldBitsEncodingFunction

Parity5:4 00 = none, 01 = even, 10 = odd, 11 = unused (falls back to none) parity_reg

A frame on the wire, LSB-first, both directions:

idle'1' start'0' d0 d1 … d(N-1) parityoptional stop'1' stopoptional idle'1'

N = the decoded data-bit count (7/8/9); the parity cell only exists when parity ≠ none; the second stop cell only exists when stop bits = 2. Every cell occupies exactly BAUDRATE clock cycles.

Transmit

Tx_Idle → Tx_Start_Bit → Tx_Data_Bits → [Tx_Parity_Bit] → Tx_Stop_Bits → Tx_Complete

A write to TX_DATA while idle (and, if CTS enable is set, cts_i = '1') latches the byte into reg_tx_data and starts the state machine. Each state drives tx_o for exactly BAUDRATE cycles before advancing: the start bit ('0'), datawidth data bits LSB-first, an optional parity bit (even = XOR of the data bits, odd = its complement), then stopbits stop bits ('1'). STATUS.TX_ACTIVE is set for the whole transmission and clears again in Tx_Complete.

Receive

Rx_Idle → Rx_Start_Bit → Rx_Data_Bits → [Rx_Parity_Bit] → Rx_Stop_Bit → Rx_Complete

rx_i passes through a 2-stage synchronizer (rx_shift_reg) before the state machine ever looks at it, so a metastable sample on the async input line can't propagate into the frame logic. Rx_Idle watches for the falling start-bit edge, then Rx_Start_Bit waits to the middle of the bit ((BAUDRATE-1)/2 cycles) and re-checks the line is still low before committing - a mid-bit glitch that already returned high is treated as a false start and the machine goes straight back to Rx_Idle.

From there every bit is centered and sampled once per BAUDRATE-cycle slot, LSB-first into rx_data. If parity is configured, Rx_Parity_Bit recomputes the expected parity from the received data bits and compares it against the bit actually seen on the wire, latching any mismatch into STATUS.PARITY_ERROR - the byte itself is still accepted either way. On the final stop bit, reg_rx_data is updated and STATUS.RX_READY set.

Interrupts

single source, level-tied to STATUS.RX_READY

Unlike GPIO's edge-latched flags, the RX_READY interrupt is a level: every cycle STATUS.RX_READY = '1' and INT_CONFIG bit 0 is set, the "set the interrupt flags" branch re-asserts INT_STATUS bit 0. A software write to INT_STATUS only wins the one cycle it happens on - if the byte is still unread the very next cycle re-fires the flag.

Clearing at "write 0" (second column) doesn't stick - STATUS.RX_READY is still '1', so the flag is back to '1' one cycle later. Only once RX_DATA has actually been read does a following clear hold, since the "set" branch's condition is no longer true. irq_o is a direct combinational read of INT_STATUS bit 0, so it tracks the table exactly.

Notes

Clear the flag by reading, not just writing

Because INT_STATUS is tied to STATUS.RX_READY, an ISR must call tinymcu_uart_getc() (or read RX_DATA directly) before tinymcu_uart_irq_clear() - clearing first just gets overwritten the next cycle.

No hardware baud divider

BAUDRATE holds the raw cycle count per bit, not a prescaler value - the caller computes clk_i frequency / desired baud rate itself before writing it.

CONFIG changes never disturb an in-flight frame

databits_reg/stopbits_reg/parity_reg are only evaluated once, in Tx_Idle/Rx_Idle - a new frame always picks up the latest CONFIG, but one already in progress keeps running with whatever it latched at its start.

Only one interrupt source

There's no TX_ACTIVE or PARITY_ERROR interrupt - INT_CONFIG/INT_STATUS only ever cover RX_READY (bit 0), unlike GPIO's one-bit-per-pin scheme.
