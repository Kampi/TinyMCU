The 3-stage pipeline

IF → ID (buffer) → EX, built around a synchronous-read (BRAM-style) instruction memory. Every register read costs one cycle of latency, so the fetch address has to be buffered one stage ahead of the instruction it produces - and every stall or redirect has to unwind exactly that buffering to avoid losing an instruction. Signal names below match tinymcu_cpu.vhd directly.

Datapath

what each stage holds

pc_reg always addresses the word being fetched this cycle. Because tinymcu_imem's read is registered, the matching instruction doesn't arrive until the next cycle - so pc_if exists purely to carry the address forward one cycle so it stays paired with instr_if when it lands.

Hazard & redirect logic

Each card names the exact register from the datapath above that it drives - that's the box it "belongs to".

stall (cpu_req.stb & !cpu_rsp.ack) | mult_busy | div_busy → pc_reg, pc_if, pc_ex, instr_ex freezes all three stages at once, verbatim
stall_d1 reg(stall) → resume_flush only internal timing helper, drives no pipeline register itself

Timing - taken branch

redirect resolves in EX, two fetches already in flight get squashed

Branch B resolves in EX at c3. By then pc_reg has already moved two steps past it - C and D were fetched speculatively down the not-taken path. redirect retargets pc_reg immediately, but the two wrong-path instructions already sitting in the pipe still have to drain as NOPs before target X reaches EX at c6.

Timing - stall then recover

e.g. MUL/DIV busy, or a load/store waiting on cpu_rsp.ack

M stalls EX for three cycles (c0-c2); the whole front end freezes with it, so N - the instruction right behind it - sits un-advanced in pc_if the entire time. The moment stall drops, resume_flush fires for exactly one cycle: it rewinds pc_reg back to pc_if instead of letting it advance, re-issuing the fetch for N that would otherwise have been silently skipped. Two bubbles later, N lands correctly in EX at c6.
