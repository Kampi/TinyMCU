The 3-stage pipeline

IF → ID (buffer) → EX, built around a synchronous-read (BRAM-style) instruction memory. Every register read costs one cycle of latency, so the fetch address has to be buffered one stage ahead of the instruction it produces, and every stall or redirect has to unwind exactly that buffering to avoid losing an instruction. Signal names below match tinymcu_cpu.vhd directly.

Datapath

what each stage holds

pc_reg always addresses the word being fetched this cycle. Because tinymcu_imem's read is registered, the matching instruction doesn't arrive until the next cycle, so pc_if exists purely to carry the address forward one cycle so it stays paired with instr_if when it lands.

Hazard & redirect logic

Each card names the exact register from the datapath above that it drives; that's the box it "belongs to".

stall ex_stall | fetch_stall → pc_reg, pc_if, pc_ex, instr_ex freezes all three stages at once, verbatim, regardless of which term is asserted
ex_stall (cpu_req.stb & !cpu_rsp.ack) | mult_busy | div_busy → ex_stall_d1 the EX-stage instruction itself can't finish yet (bus wait, MUL/DIV busy)
fetch_stall in_xip_window & !xip_fetch_ready → stall (not ex_stall_d1) an in-flight XIP fetch isn't ready yet, deliberately kept out of ex_stall/ex_stall_d1, see the note below
ex_stall_d1 reg(ex_stall) → resume_flush only internal timing helper, drives no pipeline register itself; keyed on ex_stall, not the full stall
resume_flush ex_stall_d1 & !ex_stall → pc_reg (rewind) + instr_ex (→ NOP) fires the one cycle an EX-stage stall just cleared; never for fetch_stall alone
redirect is_trap | is_mret | is_jal | is_jalr | (is_branch & branch_taken) → next_pc → pc_reg decoded from instr_ex, resolved in stage 3 (EX)
redirect_d1 reg(redirect | resume_flush) → instr_ex (→ NOP), one cycle later redirect and resume_flush share this one squash register

Why fetch_stall doesn't drive resume_flush

ex_stall (bus wait, MUL/DIV busy) stalls because the instruction already sitting in EX can't finish. pc_reg/ pc_if were coasting speculatively down the correct linear path the whole time, so once the stall clears, rewinding pc_reg back to pc_if ( resume_flush) cleanly re-issues the fetch that would otherwise be skipped. fetch_stall is different: it stalls because pc_if itself, the fetch this engine is currently waiting on, targets the XIP flash window and isn't ready yet. At that point pc_reg may already hold the very next address (or, right after a redirect into the flash window, a fresh jump target that hasn't reached pc_if yet). Rewinding it to pc_if here would silently discard that redirect and resume the stale, already-squashed fall-through path instead, so ex_stall_d1/ resume_flush are deliberately keyed on ex_stall alone, never on fetch_stall.

For the same reason, tinymcu_imem_xip.vhd's own fetch_addr_i is wired to pc_if, not pc_reg (see memory.html's flash window entry), matching how RAM/RAM disk arbitration already keys off pc_if in tinymcu_imem.vhd. The XIP read engine holds only a 1-entry cache of its most recently completed fetch; tracking pc_reg there let that entry get silently overwritten by a newer, unrelated request before pc_if ever consumed the one it was actually waiting for.

Timing: taken branch

redirect resolves in EX, two fetches already in flight get squashed

Branch B resolves in EX at c3. By then pc_reg has already moved two steps past it: C and D were fetched speculatively down the not-taken path. redirect retargets pc_reg immediately, but the two wrong-path instructions already sitting in the pipe still have to drain as NOPs before target X reaches EX at c6.

Timing: stall then recover

e.g. MUL/DIV busy, or a load/store waiting on cpu_rsp.ack

M stalls EX for three cycles (c0-c2); the whole front end freezes with it, so N, the instruction right behind it, sits un-advanced in pc_if the entire time. This is an EX-stage stall (bus wait or MUL/DIV busy), so stall and ex_stall are identical throughout; fetch_stall never engages here. The moment ex_stall drops, resume_flush fires for exactly one cycle: it rewinds pc_reg back to pc_if instead of letting it advance, re-issuing the fetch for N that would otherwise have been silently skipped. Two bubbles later, N lands correctly in EX at c6. (An XIP fetch_stall freezes the same four registers but must not trigger this rewind, see the note above.)
