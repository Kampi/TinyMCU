Memory Layout

Every bus target is selected by a single top-byte compare (addr[31:24]), so the address space is really just 256 possible 16 MB windows - only four are wired up. Nothing below that top byte is range-checked against the region's real size, so a region smaller than its window mirrors throughout the rest of it (see the SRAM note below).

Address Map

addr[31:24], tinymcu_addr_decoder.vhd

256 possible top-byte values, 4 actually decoded. Every unlabeled segment reads back as 0 and acks immediately - there is no bus fault, no stall.

Boot ROM / Flash

rtl/core/tinymcu_imem.vhd
RangeSizeStatusNotes
0x0000_0000-0x0000_7FFF 32 KB real Boot ROM. tinymcu_imem_bootrom.vhd, sized by IMEM_ADDR_WIDTH (default 13 → 213 words). Synchronous read, BRAM-inferable - one cycle of latency on both the fetch and data-side port (see the pipeline doc's IF stage). Holds whatever scripts/hex2rom.py last wrote into it.
0x0000_8000-0x00FF_FFFF ≈ 16 MB − 32 KB reserved Flash + XIP. Reserved in tinymcu_pkg.vhd (FLASH_BASE/FLASH_END) and in sw/linker.ld's FLASH output region, but tinymcu_imem.vhd only ever instantiates the Boot ROM - reads up here currently return 0.

Kernel/TPA SRAM

rtl/core/tinymcu_sram.vhd (tinymcu_ram_subsystem), tinymcu_sram_generic.vhd
RangeSizeStatusNotes
0x0200_0000-0x0200_FFFF 64 KB physical real RAM_ADDR_WIDTH default 14 → 214 words, word-addressed (addr_i = req_i.addr(ADDR_WIDTH+1 downto 2)). Synchronous read, same BRAM-style one-cycle latency as the Boot ROM. Both a data port (loads/stores) and an independent fetch port - real RISC-V cores execute out of RAM as a matter of course, an OS kernel loaded here by its own bootloader and run directly from here is the normal case, not a special one; see the Pipeline doc's IF stage. A second instance of the exact same tinymcu_sram.vhd block, both wrapped together by tinymcu_ram_subsystem, backs the RAM Disk below, at its own RAMDISK_ADDR_WIDTH.
Aliasing

tinymcu_sram_generic.vhd only ever looks at the low ADDR_WIDTH address bits - nothing above that is checked. The 64 KB array therefore repeats every 64 KB across the entire 16 MB 0x0200_0000 window; e.g. 0x0201_0000 aliases 0x0200_0000.

Linked vs. physical

sw/linker.ld only carves out 1 KB for its RAM output section (_stack_top sits at 0x0200_0400), well short of the full 64 KB the hardware actually provides - headroom for the small sw/* test programs, not a hardware limit. CP/M Neo (sw/cpm-neo/) uses the entire block for its kernel + TPA (Transient Program Area, where the CCP and .COM programs run) - it does not touch sw/linker.ld at all, see the repo README's CP/M Neo section.

RAM Disk

rtl/core/tinymcu_sram.vhd (tinymcu_ram_subsystem) - gated by RAMDISK_ENABLE
RangeSizeStatusNotes
0x0300_0000-0x0301_FFFF 128 KB physical real, when enabled A second, independent instance of the same SRAM block as above (both live inside tinymcu_ram_subsystem, see tinymcu_sram.vhd), sized by its own RAMDISK_ADDR_WIDTH (default 15 → 215 words) and decoded at its own top byte (RAMDISK_TOP_BYTE in tinymcu_addr_decoder.vhd) instead of sharing the kernel/TPA SRAM's address space. Ordinary general-purpose memory at the hardware level - readable/writable as data and fetchable as code exactly like the kernel/TPA SRAM above, not a special "disk" construct. TinyMCU has no SPI/SD controller yet, so sw/cpm-neo/platform/tinymcu/bios.c's bios_read()/bios_write() use it to back the CP/M Neo disk image instead - that 512 B-sector "disk" framing is a software convention on top of plain memory, not anything this block or the bus enforce. Content is baked in at synthesis time by scripts/cpm_neo_ramdisk2rom.py (rtl/Makefile's cpm-neo-ramdisk target).
RAMDISK_ENABLE

tinymcu_cpu.vhd's RAMDISK_ENABLE generic (default true) is threaded through three places at once: tinymcu_sram.vhd's ENABLE generic (when false, no SRAM array, no BRAM for this block at all, not merely an empty one), tinymcu_addr_decoder.vhd's top-byte compare for 0x03 on the data bus, and tinymcu_imem.vhd's fetch-side arbiter (see the Pipeline doc's IF stage) - so a disabled RAM disk is unreachable for both data and instruction fetch, not just one. When disabled, 0x0300_0000-0x03FF_FFFF behaves exactly like any other unmapped address: reads 0, acks the same cycle, and the CPU can never end up executing there even if PC somehow pointed at it. Classic (non-cpm-neo) builds disable it (rtl/Makefile's disable-ramdisk target, which runs automatically before every sw/* test program build) - those only ever need to execute out of the Boot ROM.

Peripherals

rtl/peripherals/tinymcu_periph.vhd, addr[31:8]

Same top-byte-style trick one level down: each peripheral gets a fixed 256 B window, selected by addr[31:8]. Registers below are word-aligned offsets inside that window; matches sw/lib/tinymcu_*.h exactly.

GPIO 0x0400_0000
0x00CONFIGgeneral-purpose, no defined bits yet
0x04DDRdirection, 1 = output
0x08PULL_SEL1 = pull-up, 0 = pull-down
0x0CPULL_EN1 = pull active
0x10OUToutput level, DDR = 1 pins only
0x14INread-only, actual pin level
Timer 0x0400_0100
0x00CONFIGbits 3:0 = CLKSEL
0x04INT_CONFIGbit 0 = compare IRQ enable
0x08INT_STATUSbit 0 = compare flag, write 0 clears
0x0CCOUNTERfree-running, ticks at CLKSEL rate
0x10COMPAREcompare target for the IRQ

0x00CONFIGdata bits / stop bits / parity
0x04BAUDRATEclk_i cycles per bit
0x08STATUSbits 2:0, see TX_ACTIVE/RX_READY/PARITY_ERROR
0x0CTX_DATAwrite to start a transmission (idle only)

Unmapped peripheral space

0x0400_0300-0x04FF_FFFF is not decoded by tinymcu_periph.vhd - reads as 0, same as any other unmapped address. Room for future peripherals without touching the top-level decoder.
