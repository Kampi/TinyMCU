TinyMCU · rtl/tinymcu_pkg.vhd

Bus Protocol

One request/response record pair (bus_req_t / bus_rsp_t), one outstanding transaction at a time, no pipelining. Every target either acks the same cycle (peripherals) or one cycle later (ROM/RAM) - there is no other latency in the system. See memory.html for exact address ranges and pipeline.html for how a wait state turns into pipeline bubbles.

Signals

rtl/tinymcu_pkg.vhd

One bus_req_t travels from master to target, one bus_rsp_t travels back - every device on the bus (tinymcu_sram, tinymcu_imem, tinymcu_periph_*) speaks the exact same pair of records.

bus_req_t - master → target

FieldWidthMeaning

ben4byte enable, one bit per byte lane

bus_rsp_t - target → master

FieldWidthMeaning

Handshake

stb / ack

The master raises stb and holds it - along with addr/we/ben - until it sees ack. Whether that happens the same cycle or one cycle later depends entirely on which target answered.

GPIO / Timer / UART combinational ack - zero wait states
cyclec0c1
req.stb10
rsp.ack10
stall00

*_rsp_o.ack <= *_req_i.stb; as a plain concurrent assignment in all three peripherals - no clocked process at all. The CPU's stall (cpu_req.stb and not cpu_rsp.ack) never even sees a gap, so a peripheral access costs nothing beyond the instruction's own EX cycle.

ROM / RAM registered ack - one wait state, then two pipeline bubbles
cyclec0c1c2c3
req.stb1100
rsp.ack0100
stall1000
resume_flush0100

Same registered-ack pattern in tinymcu_sram.vhd and tinymcu_imem.vhd's data port: rsp_o.ack <= req_i.stb; but inside a clocked process. One stall cycle waiting for ack, then resume_flush takes over - the exact same redirect-style two-bubble recovery a MUL/DIV stall uses (see pipeline.html's "Timing - stall then recover").

Topology

two decode levels, both plain combinational muxes

There are two separate memory-access paths out of tinymcu_cpu.vhd, and only one of them is this bus.

Fetch port pc_reg → tinymcu_imem.fetch_addr_i Not on this bus at all - no stb/ack, always-on synchronous read, one cycle of latency. See pipeline.html's IF stage.
Data bus (cpu_req / cpu_rsp) LOAD / STORE only CSR access is a separate direct connection to tinymcu_cpu_csrfile - it never touches this bus or stb/stall.

Notes

err is computed, not consulted

Both decode levels drive err <= '1' when nothing matched, but tinymcu_cpu.vhd never reads cpu_rsp.err anywhere. An unmapped access just silently reads back 0 with an immediate ack - no trap, no stall.

ben gates reads too

tinymcu_sram.vhd is four 8-bit lanes, each with its own en_i driven straight from ben. A byte/half-word load only strobes the lane(s) it actually needs - the disabled lanes hold stale data, which is fine since nothing reads them that cycle.

No outstanding transactions

The master only ever has one request in flight: stall freezes the whole pipeline (see pipeline.html) until ack arrives, so a second stb can never overlap the first.

stb naturally self-clears

cpu_req.stb is decoded straight from instr_ex's opcode. Once ack lands, the following bubble cycle (see resume_flush) turns instr_ex into a NOP, which drops stb on its own - no explicit one-shot logic needed.
